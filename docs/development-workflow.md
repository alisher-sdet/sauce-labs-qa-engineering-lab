# Development Workflow

Регламент изменения и проверки проекта Sauce Labs QA Engineering Lab.

## 1. Проверка исходного состояния

Перед началом задачи выполни:

```bash
git status --short
git branch --show-current
git log -5 --oneline
```

- Проверь незакоммиченные изменения. Не удаляй и не перезаписывай их без согласования.
- Уточни текущую ветку и последние коммиты.
- Если рабочее дерево содержит изменения, определи их назначение до начала работы.
- Перед работой с актуальной `main` проверь состояние `origin/main`. Не выполняй автоматически reset или rebase.

## 2. Определение объёма задачи

До изменения файлов:

- Сформулируй ожидаемый результат и критерии готовности.
- Определи затрагиваемый домен: Web UI, API, Mobile, CI/CD или документация.
- Изучи соответствующие тесты, конфигурацию и архитектурные ограничения.
- Выбери минимальный объём изменений, достаточный для решения задачи.

## 3. Внесение изменений

- Сохраняй существующую архитектуру и разделение тестовых доменов.
- Не добавляй зависимости и абстракции без обоснованной необходимости.
- Добавляй или корректируй тесты при изменении поведения.
- Обновляй документацию, если меняются команды, конфигурация или ожидаемое поведение.
- Не изменяй несвязанные файлы.

## 4. Локальные проверки

Выбирай проверки в соответствии с изменёнными компонентами.

### Web и API

Из каталога `web-api`:

```bash
npm run typecheck
npm run lint
npm run format:check
npm test
```

Для API-тестов, использующих локальный httpbin, предварительно запусти сервис согласно `README.md`.

### Mobile

Из каталога `mobile`, при доступных Android Emulator и Appium:

```bash
uv run --locked ruff check .
uv run pytest -v
```

### Документация и конфигурация

- Выполни `git diff --check`.
- Проверь ссылки, команды и соответствие документации реальной конфигурации.
- Для изменений CI/CD выполни доступные локальные проверки и проверь GitHub Actions после публикации.

Не считай непроверенный результат успешным. Если проверка недоступна из-за окружения, явно зафиксируй это.

## 5. Проверка изменений

Перед staging проверь состояние репозитория:

```bash
git status --short
git diff --check
git diff --stat
git diff
```

Эти команды показывают изменения в отслеживаемых файлах, но не содержимое новых файлов, ещё не добавленных в Git.

Для каждого нового файла:

- открой файл в редакторе или просмотри его содержимое;
- проверь, что он относится к текущей задаче;
- убедись, что в нём нет секретов, случайных данных и лишнего содержимого.

Перед staging убедись, что:

- изменены только относящиеся к задаче файлы;
- новые файлы проверены отдельно;
- нет случайных отчётов, локальных конфигураций или секретов;
- тесты соответствуют ожидаемому поведению;
- соблюдены архитектурные ограничения проекта.

Не выводи значения секретов в терминал или переписку.

После добавления выбранных файлов в staging обязательно проверь полный подготовленный diff согласно разделу 6.

## 6. Staging и проверка подготовленных изменений

Добавляй только необходимые файлы:

```bash
git add path/to/file
```

Перед коммитом:

```bash
git status --short
git diff --cached --check
git diff --cached --stat
git diff --cached
```

Если в staging попали лишние изменения, убери их из staging, не удаляя содержимое файлов.

## 7. Коммит

Создавай коммит только после успешных обязательных проверок и проверки staged diff.

Примеры сообщений:

```text
docs: add development workflow
test(api): cover authentication contract
test(web): add inventory sorting coverage
ci: improve test reporting
```

После коммита проверь результат:

```bash
git log -1 --oneline
git status --short
```

## 8. Push и CI

Push — отдельный этап, который выполняется после согласования:

```bash
git fetch origin
git status -sb
git push origin main
```

Перед push проверь, что удалённая ветка не содержит неожиданных изменений и локальные коммиты готовы к публикации.

После push:

- проверь запуск GitHub Actions;
- проверь статус обязательных jobs;
- изучи логи и артефакты при ошибках;
- исправь проблему и повтори необходимые проверки.

Не объявляй задачу завершённой, пока обязательные проверки не прошли либо ограничения не описаны явно.

## 9. Рабочий порядок

- Выполняй одну команду за раз и анализируй её результат перед следующим шагом.
- Не переходи к коммиту или push автоматически.
- Не отменяй существующие пользовательские изменения без согласования.
- При ошибке сначала установи причину; не обходи проверку только ради зелёного результата.

Подробности Git-команд см. в [Git Commands Cheat Sheet](git-commands.md).
